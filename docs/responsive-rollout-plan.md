# خطة استكمال Responsive في Wasla

تاريخ المراجعة: 6 أكتوبر 2026.

تحديث التنفيذ: [نتائج الدفعة الأولى وما تبقّى](responsive-rollout-progress.md).

النطاق: استكمال باقي المشروع بنفس اتجاه Superadmin وReception، مع الحفاظ على الهوية الحالية وسلوك الصلاحيات والعمليات. هذه وثيقة تخطيط مبنية على مراجعة الكود؛ لا تعني أن الصفحات اختُبرت الآن في المتصفح أو أن التنفيذ اكتمل.

## 1. نتيجة المراجعة

- المشروع يستخدم Angular 21 وBootstrap 5.3، والمكونات مستقلة وملفات الأنماط CSS.
- `PageHeader` يستخدم بالفعل `container-type` و`@container`؛ هذا هو المرجع لهيدر صفحات الإدارة والبوابات.
- Reception والحجوزات وبعض الشاشات المالية تستخدم Container Queries وإعادة ترتيب الصفوف؛ نعيد استخدام الفكرة حسب طبيعة البيانات، دون استيراد ملفات CSS الخاصة بـAdmin إلى ميزات أخرى.
- `browser-admin-responsive.cjs` يغطي حاليًا doctors وsuperadmins وreservations. هذه تغطية محددة، وليست دليلًا على اكتمال جميع صفحات Admin.
- `browser-reception-responsive.cjs` يغطي workspace وpatients وfamily-requests وreservations وqueue وfinance بالعربية والإنجليزية وعلى ثمانية عروض.
- `browser-auth-responsive.cjs` يغطي login فقط؛ باقي رحلة التسجيل واسترجاع الحساب تحتاج تغطية مستقلة.
- `browser-mobile-navigation.cjs` يوفر أساسًا لاختبار الهيدر والتنقل والصلاحيات، لكن تغطية التنقل لا تكفي لإثبات صلاحية محتوى كل صفحة.
- صفحات Phase 14 تستخدم `shared/styles/directory-workspace.css`. التقرير الموجود يسجل فحصًا على 390 و1440 فقط؛ يلزم استكمال أحجام التابلت والأحجام المتوسطة والحالات التفاعلية.
- Doctor Practices يحتوي نحو 4,278 سطر CSS موزعة على خمسة ملفات، وPatient نحو 2,843 سطرًا في ملفين، وPublic Doctors نحو 2,446 سطرًا. الحجم مؤشر لأولوية المراجعة، وليس دليلًا منفردًا على وجود كود غير مستخدم.
- `SideDrawer` يحتوي قواعد اتجاه متعددة و`!important` في التموضع ونسخة الموبايل. Finance وTickets يحتويان أيضًا `!important` قائمًا؛ تنظيف القواعد الأصلية مطلوب قبل تعميمها.
- بعض الصفحات تستخدم `overflow-x: hidden`، وPatient Tickets يستخدم `100vh` في التفاصيل. نتحقق من أن الإخفاء لا يخفي محتوى فعليًا، ومن سلوك الارتفاع مع لوحة مفاتيح الهاتف.
- `doctor-onboarding` و`public-doctor-details` لا يستخدمان `app-page-header` حاليًا. يلزم توحيد هيدر صفحة onboarding والتحقق من هيدر تفاصيل الطبيب داخل البوابة؛ صفحات Auth والصفحات القانونية العامة لها سياق مختلف.

## 2. اتفاق موحد للتنفيذ

### ملكية الأنماط

1. App والـlayouts يمتلكون هيكل الشاشة، التنقل، مساحة المحتوى والفوتر.
2. المكونات المشتركة تمتلك استجابتها: PageHeader وSideDrawer وAppHeader وMobileNavigation وPlatformFooter وToastContainer.
3. الأنماط المشتركة تحتوي قواعد العرض العامة فقط. منطق الطبيب أو المريض أو الدواء يبقى داخل ميزته.
4. قبل استخراج قاعدة مشتركة، نثبت وجود استخدامها في ميزتين مستقلتين ونحدد مالكها، ثم نحذف النسخ المحلية التي تستبدلها.
5. لا ننشئ مكون جدول عام أو خدمة responsive جديدة لمجرد توحيد أسماء الكلاسات. نعيد استخدام Bootstrap والقواعد الموجودة أولًا.

### سلوك الأحجام

| السياق | السلوك المطلوب |
| --- | --- |
| هاتف أقل من 576px | عمود واحد للفورم، بحث واضح، إجراءات تلتف دون قص، drawer بعرض الشاشة |
| شاشة صغيرة 576–767px | عمودان للحقول القصيرة عندما يتسع المحتوى، وتنقل الموبايل الحالي |
| تابلت 768–991px | layout متوسط فعلي، navigation drawer، فلاتر مرنة دون ضغط الجدول |
| Desktop من 992px | الحفاظ على sidebar الحالي ومساحة العمل، مع تكييف المحتوى حسب عرضه المتاح |
| شاشات واسعة | ضبط عرض منطقة القراءة دون تضييق الفوتر أو تمديد الحقول بلا داعٍ |

هذه حدود Bootstrap المرجعية؛ استجابة مكونات المحتوى تعتمد على عرض الحاوية عندما يوجد sidebar أو drawer. لا نبدل كل breakpoint قائم آليًا، ونختبر جانبي أي حد يتغير.

### قواعد العرض

- Mobile-first عند إعادة كتابة الجزء المستهدف، مع `min-width: 0` و`minmax(0, 1fr)` وخصائص المسافات المنطقية.
- قوائم الأشخاص والحجوزات: صفوف مترابطة مع تسميات حقول ظاهرة على الهاتف، دون تحويلها إلى كروت منفصلة ودون حذف إجراء أساسي.
- جداول الاستيراد والمقارنة والبيانات المالية التي تحتاج مقارنة أعمدة: تمرير أفقي داخل حاوية الجدول فقط، مع بقاء عنوان الصفحة والإجراءات في مجال الرؤية.
- لا نستخدم إخفاء overflow على الصفحة كحل لخلل التخطيط.
- النماذج: 42px للحقول وفق النظام الحالي؛ أهداف لمس الأزرار والإغلاق والتنقل 44px على الأقل. لا نجعل الرسم الصغير للتoggle هو مساحة اللمس الوحيدة.
- التفاصيل والمراجعات والتحرير السريع داخل drawer؛ على الهاتف بعرض كامل، مع scroll داخلي وحفظ موضع القائمة بعد الإغلاق.
- الفوتر مشترك داخل App، بعرض كامل ويستقر أسفل الصفحة باستخدام flex، مع التحقق من عدم حجبه أو حجب الإجراءات بواسطة التنقل السفلي.
- جميع النصوص والتوستات AR/EN، والأرقام والهواتف والتوقيتات LTR حيث يلزم. لا نضيف حدودًا ملونة أو blinking أو nested cards.

## 3. مراحل التنفيذ مرتبة حسب الاعتماد

### المرحلة 0 — تثبيت المرجع وجرد التغطية

**العمل:**

- استخراج قائمة المسارات الفعلية من root routes وfeature routes، مع الدور والصلاحيات والـlayout لكل مسار.
- تشغيل الفحوص القائمة لـAdmin وReception وLogin والتنقل وتسجيل baseline قبل أي تغيير مشترك.
- تسجيل DOM nodes وعدد CSS selectors وحجم CSS في الصفحات المستهدفة، مع الصور والحالات المغطاة.
- لكل مكون: ربط selectors بالـHTML والحالات الديناميكية؛ مراجعة تكرار القواعد داخل نفس نطاق media/container. تكرار selector بين نطاقين مختلفين ليس خطأ تلقائيًا.
- فصل الاختبارات الناجحة عن المسارات غير المغطاة، وحفظ أي فشل سابق مستقلًا عن التغيير الجديد.

**التسليم:** جدول مسارات وحالات + baseline يمكن المقارنة به. لا نبدأ تعديلات مشتركة قبل وجوده.

### المرحلة 1 — المكونات المشتركة والـshell

**الملفات:** `src/app/app.*`، `shared/components/{portal-layout,app-header,mobile-navigation,page-header,side-drawer,platform-footer}`، `shared/toast`، `shared/styles/directory-workspace.css` و`src/styles.css` عند الحاجة فقط.

**العمل:**

- تدقيق تداخل padding بين layout والصفحة والهيدر؛ تعيين مالك واحد لكل مساحة.
- تنظيف SideDrawer من `!important` وقواعد التموضع المتضاربة، وتوحيد جهة الفتح وفق متطلبات RTL/LTR، مع فحص جميع المستهلكين قبل التغيير.
- اختبار focus trap وEscape وإرجاع focus ومنع scroll للخلفية، وإصلاح الناقص في المكون المشترك.
- مراجعة ترتيب طبقات drawer والتنقل والتوست، وsafe-area وارتفاع `100dvh` ولوحة المفاتيح.
- استكمال استجابة الفلاتر وpager وdetail forms في directory-workspace دون تسريب selectors إلى مكونات لا تحتاجها.
- تثبيت صلاحية الهيدر والفوتر في الصفحات القصيرة والطويلة، وحالات sidebar المفتوح والمغلق.

**بوابة الخروج:** نجاح regression لـSuperadmin وReception والتنقل، مع drawer داخل حدود الشاشة وإغلاق متاح في الاتجاهين.

### المرحلة 2 — بوابة الطبيب وإدارة العيادة

**الموديولات والمسارات:**

- Workspace: `/workspace/doctor`.
- Doctor Practices: `/doctor/practices` ومسارات التفاصيل الموجودة داخل feature routes.
- Practice Editor،Schedule،Segments،Operations.
- Doctor Profile وPublic Profile Manager: `/doctor/profile`.
- Doctor Receptions: `/doctor/receptions`.
- Doctor Onboarding: `/doctor/onboarding`.

**العمل:**

- جعل اختيار العيادة والمعلومات الأساسية والإجراء الرئيسي واضحين دون ازدحام.
- تعديل شبكات العيادات والجداول ومواعيد العمل حسب عرض المحتوى الفعلي؛ مراجعة حدود مثل `minmax(360px, 1fr)` داخل Segments.
- الحفاظ على سياق اختيار العيادة والتبويب أثناء فتح التحرير وإغلاقه.
- ترتيب فورم العيادة والملف الشخصي عمودًا واحدًا على الهاتف، ثم أعمدة إضافية عند الاتساع.
- عرض مساعدي العيادة كقائمة موحدة، مع وصول مباشر للإجراءات المسموحة.
- توحيد onboarding مع PageHeader، وتبسيط خطواته ورفع الملفات والأخطاء على الهاتف.

**بوابة الخروج:** إمكانية مراجعة العيادة وتعديل بياناتها ومواعيدها وصلاحيات المساعدين دون قص الحقول أو ضياع زر الحفظ؛ mutations مفحوصة ببيانات اصطناعية وتوست مترجم.

### المرحلة 3 — العمليات اليومية المشتركة

**الموديولات:** Reservations وTickets وFinance.

**المسارات:** `/doctor/reservations`، `/patient/reservations`، `/doctor/queue`، `/patient/tickets`، `/doctor/finance`، `/doctor/revenue`، `/patient/finance`. مسارات Reception وAdmin المقابلة regression إلزامي.

**العمل:**

- استكمال ما بدأ في Reception على نفس المكونات حسب اختلاف الدور، بدل نسخ واجهة مستقلة لكل بوابة.
- مراجعة Reservation Editor وDetails وCheck-in وحالات التعارض والحقول والتواريخ داخل drawer.
- تبسيط صف التذكرة: الرقم والطبيب والموعد والحالة والإجراء، مع ارتفاع تفاصيل مناسب للهاتف.
- مراجعة اختيار التاريخ والعيادة وملخصات الإيراد وpagination، وتنظيف `!important` في Finance وQueue ضمن الأجزاء التي تُعاد كتابتها.
- التأكد من أن اختلاف الدور لا يخفي حقولًا أو إجراءات مصرحًا بها ولا يعرض إجراءات محظورة.

**بوابة الخروج:** لا regression في Reception، وتغطية الطبيب والمريض والصلاحيات المختلفة بوضوح.

### المرحلة 4 — الكشف والروشتات والموديولات الطبية الجديدة

| الموديول | المسارات/المكونات | أهم التعديلات والفحوص |
| --- | --- | --- |
| Encounters | `/doctor/encounters`، `/patient/encounters` | القائمة والتفاصيل والتشخيصات والتعديل؛ التفاف الإجراءات وغياب أي قص داخل drawer |
| Prescriptions | `/doctor/prescriptions`، `/patient/prescriptions`، PrescriptionWorkspace داخل الكشف | بحث الدواء والنتائج والجرعة والمدة والتكرار؛ nested content يعتمد على عرض drawer لا viewport |
| Medication Requests | `/doctor/medication-requests`، `/drug-catalog-requests` | طلب إضافة دواء ومراجعته مع اختلاف صلاحيات الطبيب ومدير الدليل |
| Drug Catalog | `/drug-catalog` | البحث والفلاتر والتحرير والدمج والتاريخ، مع احتواء الأسماء الطويلة |
| Drug Imports | `/drug-catalog/imports` | رفع الملف والمعاينة والمقارنة والصفحات والأخطاء؛ scroll محلي لجداول المقارنة |
| Catalog Managers | `/admin` + مسار مدير الدليل المسجل في `admin.routes.ts` | مراجعة القائمة والفورم الجديدين ضمن نمط Admin المعتمد |

**حدود العمل:** ملفات `domains/drug-catalog` والعقود وخدمات API ليست هدف responsive. التغيير في العرض ومكوناته فقط إلا إذا ثبت احتياج سلوكي محدد. لا نغير الحماية أو قواعد الإكمال أو إدارة concurrency من أجل تعديل layout.

**بوابة الخروج:** اختبار الروشتة داخل الكشف وكذلك صفحاتها المستقلة، وعرض المريض للقراءة فقط، وpreview/apply للاستيراد بردود اصطناعية دون أي تعديل لبيانات حقيقية.

### المرحلة 5 — بوابة المريض ورحلة البحث والحجز

**الموديولات:** Workspace Patient،Patient Profile،Patient Family،Follow-ups،Public Doctors،Public Doctor Details.

**المسارات:** `/workspace/patient`، `/patient/profile`، `/patient/family`، `/patient/follow-ups`، `/doctors`، `/doctors/:doctorId`.

**العمل:**

- إزالة تكرار قواعد الهيدر والخلفيات والمساحات بين profile وfamily بعد تحديد المستهلكين، وتبسيط DOM الزخرفي غير الضروري.
- مراجعة بيانات المريض وجهات الاتصال وطلبات الأسرة والرفض وإعادة الإرسال داخل forms/drawers.
- استكمال follow-ups على الهاتف، بما في ذلك أهلية الحجز والحالة الفارغة والإجراء التالي.
- مراجعة فلاتر البحث ونتائج الأطباء وأسماء التخصصات الطويلة، دون إعادة رسم أو تحميل بحث زائد عند تغيير الحجم.
- اختبار Doctor Details بوضع الزائر وبوضع المريض داخل PortalLayout، وهيدر وتبويبات ومواعيد وحجز متسقة.
- تفاصيل الطبيب العامة تظل صفحة الاكتشاف الحالية؛ تفاصيل العناصر التشغيلية والتحرير السريع تستخدم drawers.

**بوابة الخروج:** رحلة البحث ← الطبيب ← الموعد ← الحجز قابلة للإكمال على الهاتف، مع بقاء profile/family سهلة القراءة والتحرير.

### المرحلة 6 — باقي Auth والصفحات القانونية والدعم

**المسارات:** `/register/patient`، `/register/doctor`، `/forgot-password`، `/forgot-password/otp`، `/forgot-password/reset`، `/change-password`، `/privacy`، `/terms`، `/help`.

**العمل:**

- إعادة استخدام AuthLayout؛ استكمال فحص التسجيل والخطوات والتحقق ورفع الملفات وإظهار كلمات المرور.
- اختبار OTP والأخطاء والعدادات والنصوص الطويلة ولوحة مفاتيح الهاتف.
- مراجعة قراءة الشروط والخصوصية وتنقل الأقسام ونموذج الدعم على الهاتف والتابلت.
- تثبيت الفوتر العالمي ومنع تكراره في أي صفحة أو layout.

**بوابة الخروج:** اكتمال رحلة الحساب في الاتجاهين، وقراءة النصوص وإرسال الدعم دون قص أو تداخل.

## 4. طريقة تنفيذ كل دفعة

1. Audit للمكون وDOM وCSS والحالات الديناميكية والمستهلكين.
2. تحديد التصميم النهائي وملكية المسافات والقواعد قبل التعديل.
3. تعديل القواعد الأصلية وحذف HTML/CSS/TS الذي استُبدل؛ لا overrides ولا زيادة specificity ولا `!important` جديد.
4. الحفاظ على state الحالي وعدم بناء نسختين منفصلتين للصفحة على mobile/desktop. لا نكرر form أو subscriptions.
5. تحديث behavioral specs للمنطق المتأثر؛ أي مكون جديد كامل TS + HTML + CSS + SPEC.
6. فحص build والترجمة والـarchitecture، ثم المتصفح والحالات الحرجة والـregression المطلوب للدفعة.
7. تسجيل before/after والنتائج والمشكلات المتبقية قبل الانتقال للمرحلة التالية.

## 5. مصفوفة الاختبار ومعايير القبول

- **العروض الأساسية:** 320،390،600،768،820،1024،1280،1440px؛ نفحص جانبي حدود 576/768/992 وعرض أي container breakpoint يتغير.
- **الاتجاهات:** العربية RTL والإنجليزية LTR لكل مسار؛ التبديل أثناء فتح فورم/drawer أيضًا.
- **الحالات:** loading،empty مع SVG وإجراء مناسب،error/retry،populated،validation،disabled/pending،نصوص طويلة وبيانات اختيارية غائبة.
- **التفاعل:** touch وkeyboard،tab order،focus واضح،إغلاق drawer وإعادة focus،حفظ موضع القائمة،منع ازدواج الإرسال،نجاح/فشل mutation مع toast.
- **الارتفاع:** صفحة قصيرة وطويلة،landscape وارتفاع صغير،ثم لوحة مفاتيح فعلية على هاتف عندما يتاح الجهاز. المحاكاة لا تثبت سلوك الجهاز الحقيقي.
- **احتواء الشاشة:** `document.documentElement.scrollWidth <= innerWidth`؛ العناصر المهمة لا تُقص داخل صف أو drawer. التمرير المحلي للجدول مسموح عندما تتطلب البيانات ذلك.
- **الطبقات:** close/save/toast متاحة،ولا يغطي mobile navigation آخر صف أو زر أو رابط فوتر.
- **الصور:** التقاط مقارنة عربية وإنجليزية على 390 و820 و1440 على الأقل، بعد اكتمال الخطوط واستقرار drawer؛ فحص آلي لباقي الأحجام والحالات.
- **البيانات:** fixtures اصطناعية لكل دور وصلاحية؛ لا execute لمعاملات أو imports أو تغييرات حسابات حقيقية لغرض responsive QA.
- **جودة الكود:** لا قواعد مهجورة أو wrappers زائدون أو تكرار جديد؛ نراقب selectors وDOM وحجم CSS ونشرح أي زيادة لازمة، دون حذف semantics أو اختبارات لتحقيق رقم أقل.

### أدوات التحقق

- الاحتفاظ بسكربتات Admin وReception وAuth وMobile Navigation كاختبارات regression.
- استكمال browser coverage لكل مجموعة أعلاه باستخدام بنية CDP والبيانات الاصطناعية الموجودة؛ استخراج helper مشترك فقط عند وجود تكرار فعلي يستحق ذلك.
- إخراج نتائج وصور كل دفعة إلى `docs/browser-verification/responsive/<phase>/` مع route وactor وlanguage وviewport وstate ونتيجة assertions.
- `npm run build`،اختبارات المكونات المتأثرة،`npm run check:i18n` و`npm run check:architecture`. تثبيت الفشل السابق قبل البدء؛ إغلاق مخالفات الملفات المعدلة وتوثيق الباقي بدل اعتبار check فاشل نجاحًا.
- تغييرات shared تتطلب regression للمستهلكين الحاليين؛ عند النهاية تشغيل المجموعة الكاملة للاختبارات ومراجعة المسارات غير المغطاة.

## 6. ترتيب البدء ومفهوم الاكتمال

الترتيب المقترح: baseline → shared shell/drawer → Doctor Practices وبوابة الطبيب → العمليات اليومية → الكشف والروشتات والدليل → بوابة المريض والاكتشاف → Auth والقانونية.

لا نعتبر أي موديول مكتملًا بوجود media query أو screenshot واحدة. الاكتمال يتطلب اجتياز مصفوفة أحجامه ولغاته وحالاته والإجراءات الأساسية، مع حذف الكود الذي استُبدل وتسجيل أدلة التحقق. أي أجزاء Admin وReception غير الموجودة في السكربتات الحالية تُسجل كفجوة تغطية وتُفحص عند تأثرها بتغيير مشترك، دون افتراض أنها اكتملت سابقًا.
